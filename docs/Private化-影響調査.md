## 2. Private 化したときの影響

| # | 影響 | 内容 |
|---|---|---|
| 1 | **GitHub Pages が止まる可能性** | GitHub の無料プラン（Free）では、Pages は**公開リポジトリだけ**。非公開にするには有料プラン（Pro 以上）が必要（※料金・条件は公式ページで要確認） |
| 2 | **「ソースを隠す」効果は限定的** | 画面を配信する以上、ブラウザに届く JS・CSS・HTML は誰でも見られる（Private でも同じ）。**守れるのは、設計メモ・テスト・履歴・サーバー側の定義（SQL・Edge Function）** |
| 3 | **既存チームの URL** | 今の github.io の URL を使っているチームが、Pages 停止で使えなくなる恐れ（要確認：既存チームは今どの URL で使っているか） |
| 4 | **URL が変わる場合の直し箇所** | ① Supabase Auth の Redirect URLs ② Google ログインの承認済みオリジン ③ Edge Function の許可元（`CP_ALLOWED_ORIGINS`・`WF_ALLOWED_ORIGINS`）④ `deploy.yml`・`docs/HANDOFF.md` の URL の記述 ⑤ 公開ロードマップのリンク。**新しい Supabase プロジェクトを作るので、最初から本番の URL で設定すれば、直しは発生しない** |
| 5 | **Actions の使用量** | 非公開では無料の使用時間に上限がある（※数字は要確認）。現在のワークフローは軽い（デプロイ・計算ロジックの簡易テスト）ので影響は小さい見込み |
| 6 | **Netlify の存在** | `CLAUDE.md` に「親プロジェクト `netlify/` 配下を別経路で配信中」とある。このリポジトリには `netlify.toml` は無い（親側にあるはず）。**移行先の候補として使える可能性があるが、現状は未確認** |

## 3. 進め方の選択肢

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A** | いまのリポジトリを Private 化し、配信を Netlify／Cloudflare Pages などへ移す | リポジトリが 1 つで済む | 既存チームの URL が変わる・全部いっぺんに動く |
| **B（推奨）** | **SaaS 用に新しい Private リポジトリ**を作り、コードをコピーして始める。いまのリポジトリは既存チーム用にそのまま | 既存チームに影響ゼロ・新リポジトリは履歴が白紙で内部メモの履歴が持ち込まれない・SaaS 用の新しい Supabase プロジェクトと 1 対 1 で管理できる | 2 つのリポジトリを当面は別々に管理（機能の同期が手間） |
| **C** | まず現状維持で段階 1（データ分離）だけ進め、公開前に A か B を選ぶ | 急がなくてよい | 設計メモが公開のまま残る |

**推奨は B。** 新しい Supabase プロジェクトを作ると決めたので、リポジトリも新しくするのが筋が通る。ただし B の前に決めること：
1. 今のリポジトリを **今後も更新し続けるか**（既存チームのため）。続けるなら、2 つの同期の手間が出る。
2. GitHub の **プラン（Free／Pro）**。
3. **SaaS の公開ドメイン**（独自ドメインを使うか）。OAuth・許可元の設定がこれに依存するので、早めに決めるとよい。
