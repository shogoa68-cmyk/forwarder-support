# 削除の「ゴミ箱」化 設計案

作成: 2026-11-05 ／ 状態: **段階 1 の SQL を作成・手元の Postgres で試験済み（本番のデータベースには未適用・画面コードは未変更）**

- SQL: [sql/trash-quote-presets.sql](sql/trash-quote-presets.sql)
- 試験: `bash scripts/design-tests/trash-sql-test.sh`（使い捨ての Postgres で 38 項目。わざと壊した版も検出できることを確認済み）
背景: [アイデア台帳.md](アイデア台帳.md) の「セキュリティ方針」の着手順 1。心配ごとは「うっかり削除」。

---

## 1. いま何が起きているか（調べた結果）

- 案件の削除（`cloud.js` の `cloudDeletePreset`）は、確認ダイアログを1回出したあと、データベースから **その場で完全に消す**。取り消す手段はない。
- 同じ「その場で完全に消す」削除が、約 20 か所ある（案件、マスター詳細、別名、ブックマーク、取引ルール、行パターン、リマークひな形、ローカルチャージ など）。
- 案件の「消えない保険」は、編集ロック（他の人が編集中のときは消せない）だけ。
- バックアップの仕組みは、コードにも SQL にも見当たらない（Supabase 側の設定は未確認）。

> 用語メモ
> - **ソフトデリート**：消したことにして、実際はデータを残しておく方法。「ゴミ箱」はこれ。
> - **トリガー**：データベースに仕掛ける「自動で動く小さな係」。「削除されそうになったら、その前にこれをやる」と決めておける。
> - **RLS**：データベース側の鍵。誰がどのデータを見たり書いたりできるかを決める。

## 2. 方式の比較

| | A. 削除済みの印を付ける方式 | B. 削除の直前に控えを取る方式（**推奨**） |
|---|---|---|
| しくみ | 案件に `deleted_at`（消した日時）の列を足す。消すときは日時を入れるだけ | 本当に消す。ただし消える直前に、トリガーが中身をまるごと「ゴミ箱テーブル」にコピーする |
| 画面側の変更 | **大きい**。案件を読む場所が約 45 か所（一覧・統計・類似見積・比較・サブコン集計…）。1か所でも「消えていない」条件を付け忘れると、消したはずの案件が統計や候補に出てしまう | **ほぼ無い**。今までどおり「消す」だけで、読む側は何も変えなくてよい |
| 取りこぼし | 画面以外からの削除（管理画面の SQL など）は印が付かず、そのまま消える | どこから消しても控えが残る |
| 戻す作業 | 印を外すだけ | 控えから元のテーブルへ書き戻す（専用の関数を作る） |
| 向いている場面 | 「消した案件も一覧に薄く出す」など | 「うっかり消した」を救う（今回の目的） |

**B を選ぶ理由**：今回の目的は「うっかり削除を戻せること」。B なら、読む側の約 45 か所に触らずに、全部の削除を一度に守れる。付け忘れの事故が起きにくいのが一番の強み。

## 3. 設計（B 方式）

### 3-1. ゴミ箱テーブル `trash`（1つで全テーブル分をまとめる）

| 列 | 意味 |
|---|---|
| `id` | ゴミ箱の通し番号 |
| `source_table` | 元のテーブル名（例：`quote_presets`） |
| `source_id` | 元の行の ID |
| `label` | 一覧に出す名前（案件名など。`name` 列があればそれ） |
| `row_data` | 消えた行の中身まるごと（jsonb） |
| `batch_id` | 同じ削除で一緒に消えた行の目印（親を消すと連鎖で子も消えるため） |
| `deleted_by` / `deleted_at` | 誰がいつ消したか |
| `expires_at` | 完全に消える日（既定：消した日の **30 日後**） |
| `restored_at` | 戻した日時（戻したら印を付ける。履歴として残す） |

### 3-2. 削除の直前に動くトリガー（1つの関数を使い回す）

```sql
-- イメージ（実装時に精査する）
create function public.trash_on_delete() returns trigger
language plpgsql security definer set search_path = public as $$
begin
  insert into public.trash(source_table, source_id, label, row_data, batch_id, deleted_by)
  values (tg_table_name, (to_jsonb(old)->>'id'), coalesce(to_jsonb(old)->>'name', ''),
          to_jsonb(old), txid_current(), auth.email());
  return old;
end $$;
-- 対象テーブルごとに: before delete trigger を1行ずつ付ける
```

- 失敗して「削除そのものができなくなる」事故を避けるため、控えの保存に失敗しても削除は止めない書き方にするか、止めるかを実装前に決める（→ 7. 決めたいこと）。

### 3-3. 戻す関数 `trash_restore(p_id)`（security definer）

- 控えの中身を元のテーブルへ書き戻す（`jsonb_populate_record`）。
- 同じ `batch_id` の子（リンクなど）は、**親を先に**戻す。
- すでに同じ ID や同じ名前の行があって戻せないときは、理由を返して何も変えない。
- 案件は、編集ロック（`locked_by`）を空にして戻す。

### 3-4. 見える人・できる人（RLS）

| 操作 | できる人 |
|---|---|
| ゴミ箱の一覧を見る | チームメンバー（元のデータと**同じ範囲**。ゴミ箱で新しく見えるものは増えない） |
| 元に戻す | チームメンバー |
| 「完全に削除」（ゴミ箱を空にする） | **管理者のみ** |
| テーブルへの直接の書き込み | 誰もできない（トリガーと関数だけが書く） |

### 3-5. 自動で消える（期限切れ）

- 毎日、`expires_at` を過ぎた控えを消す。既存の「不具合報告の添付を 90 日で消す」（`pg_cron`）と同じ作り方。
- 期限は 30 日が出発点。短くするほど「消したはずが残る」不安が減り、長くするほど救える。

### 3-6. 画面（フェーズ 2）

- 削除の確認文を「ゴミ箱に移動します（30 日は戻せます）」に変える。取り消しにくい操作用の `uiConfirm()` を使う。
- 削除した直後のトーストに **「元に戻す」** ボタンを出す（その場のうっかりがいちばん多い）。
- ダッシュボードに「🗑️ ゴミ箱（N件）」。一覧に「名前・消した人・消した日・あと何日」「元に戻す」。管理者だけ「完全に削除」。
- 「ゴミ箱の中身も、期限が来たら完全に消える」ことを画面に書く（「削除＝その場で消える」と思っている人に誤解させない）。

## 5. 注意が必要な点（設計で先に潰す）

1. **添付ファイルの実体（Storage）はトリガーでは守れない。**
   案件の削除では、コード上は添付の実体を消していない（要確認）。さらに案件の添付は **14 日で自動削除**の仕組みがある。戻した案件の添付が先に消えている場合がある。→ 「添付は戻らないことがある」と画面に書くか、ゴミ箱にある間は自動削除から外す。
2. **連鎖削除の順番。** 親を消すと子も消える。戻すときは親→子の順。`batch_id` で一緒に扱う。
3. **同じ名前の案件があると戻せない場合がある。** 戻せないときは理由を出し、データは変えない。
4. **ゴミ箱は「消したはずの機密」の置き場でもある。** 仕入れ値・乗せ幅も入るので、見える範囲は元と同じ（メンバーのみ）にする。期限切れで確実に消す。
5. **管理者が悪意を持って空にする場合は防げない。** これは「うっかり」対策であり、持ち出し・悪意への対策は別（着手順 2）。
6. **テストは本物のデータベースで。** トリガーと関数は Postgres の機能なので、いまの擬似 Supabase のテストでは確かめられない。確認用のプロジェクト（または手元の Postgres）で、削除→戻す→期限切れ→権限の4点を確かめてから本番へ。
7. **元に戻す手順。** やめたいときは、トリガーを外せば元の挙動に戻る（ゴミ箱テーブルは残るが無害）。

## 6. バックアップ（ゴミ箱とは別の保険）

ゴミ箱は「削除」にだけ効く。「中身を上書きして壊した」「テーブルごと壊れた」は救えない。そこで別の保険が要る。

| 方法 | 内容 | 注意 |
|---|---|---|
| Supabase 標準のバックアップ | プランによっては毎日自動（上位プランは時点復元も） | **契約中のプランで有効か未確認**。まずダッシュボードで確認 |
| 自前の定期書き出し | 定期ジョブで主要テーブルを書き出して、非公開の保管場所へ | **公開リポジトリには絶対に置かない**（お客様情報・仕入れ値が入るため） |
