## 1. 何の話か

見積の「サブコン」と「キャリア（幹線輸送の船社・航空会社）」は、マスター管理（統計タブ）では別カテゴリ（`sv` と `carrier`）になっている。しかし実務では同じ会社が両方に現れる（例：Yang Ming は幹線輸送のキャリアであり、海上運賃の明細行ではサブコンとして入力される）。サブコン側に「サブコン種別」（`FCL CARRIER` など）を持てるようになったため、別カテゴリを残す理由が薄れた。これを統合するべきか、するならどう進めるか、が論点。

ユーザーへの提案（回答済み）：**統合した方がよい。ただし段階的に。**

| 段階 | 内容 | 主な影響 |
|---|---|---|
| 1 | BOOKMARK の会社名と、幹線輸送のキャリア候補を、サブコンマスター（種別がキャリア系のもの）から取る | 新しい読み取り経路の追加が中心。既存データは触らない |
| 2 | 既存の `carrier` マスターを `sv` へ移行（別名・詳細・投票を引き継ぐ） | **データ移行。SQL・衝突処理が必要** |
| 3 | `carrier` カテゴリ自体を廃止 | **統計タブの集計軸が変わる**（過去案件の集計への影響を要確認） |

段階1・2まででズレによる実害の大部分は解消する見込み。段階3は統計への影響を見てから判断。

## 2. きっかけになった事象（このセッションで起きたこと）

- 見積のサブコン別明細の見出しに「🔖 BOOKMARK」が出ない、という報告（Yang Ming）。
- 原因：ボタンの表示条件が「マスターのサブコン種別が `FCL/LCL/AIR CARRIER`」だけだった。Yang Ming はマスター登録済み（「📇 詳細」は出る）だが種別が未設定だった。
- 暫定対応（実装済み・main 反映済み）：**種別に関係なく、その名前（別名・代表名含む）でブックマークが登録されていればボタンを出す**（`bmHasBookmarks` を追加）。
- これは対症療法。根本的には「同じ会社が 2 つのカテゴリに散らばる」ことが原因。

## 3. 現状の仕組み（コードで確認済みの事実）

### マスターのデータ構造
- カテゴリ：`stats.js` の `_FIELD_LABEL = { sv, carrier, nm, un, customer, port }`（`sv`=サブコン、`carrier`=キャリアは別カテゴリ）。
- テーブル（`docs/` の SQL で確認）：
  - `master_details`（詳細）：`field` の CHECK に `'sv'` と `'carrier'` の両方がある。
  - `synonym_groups`（別名グループ）：`field` に `'sv'` / `'carrier'` あり。
  - `alias_rules`（置換ルール）：`field` に `'sv'` / `'carrier'` あり。
  - `master_votes`（マスター登録の投票）：SQL のコメントは `'sv' | 'nm' | 'un'`。**`carrier` の票がこのテーブルに入るかは未確認（要確認）。**
- 詳細項目（`alias-rules.js` 約 1528〜1535 行）：
  - `sv`：ふりがな・英語名・**サブコン種別 `svTypes`（複数・タグ形式）**・グループ ほか。種別のひな形は `通関業者 / 倉庫業者 / 運送業者 / FCL CARRIER / LCL CARRIER / AIR CARRIER / 海外代理店 / 保険会社 / サーベイヤー`。
  - `carrier`：ふりがな・英語名・グループのみ（種別なし）。
- キャリアの集計（`stats.js` 約 245〜295 行）：**幹線輸送（`z2Carrier` と航路データ）から集計**。サブコンは「明細行のサブコン欄すべて」。つまりキャリアは入力欄の由来で決まっている。
- 承認制：`master_requests` 経由の申請・承認がある（`statsIsApprovalOn()`）。統合時の移行でも承認制をどう扱うか要検討。

### 名前の照合（別名の考慮）
- `alias-rules.js`：`window.nameCanon(field, raw)`（代表名）、`nameVariants(fields, raw)`（別名を含む表記一覧）、`nameSame(field, a, b)`。
- BOOKMARK 関連は `['carrier', 'sv']` の**両方**で照合している（`bookmarks.js` の `fetchCarrierBmsForQSP` / `bmShowForCarrier` / `bmHasBookmarks`）。→ 統合後もこの呼び出しを `['sv']` だけにできる可能性がある。

### 見積タブ側
- 幹線輸送のキャリア入力欄 `#z2Carrier` の候補 `carriers-dl`：`conditions.js` の `_refreshCarrierDatalist()` が作る。内訳は ①組み込みデータ（`CARRIERS` / `CARRIERS_LCL` / `CARRIERS_AIR`。RORO・在来船は空）②**輸送モードと同じ種別のブックマーク会社**（`bmCarrierNamesForType`）③`alias-rules.js` の `_refreshDatalist` が足す `carrier` マスター。
- サブコン見出し：`row.js` の `_refreshSvHeaderChips()`。「📇 詳細」はマスター登録済みのとき、「🔖 BOOKMARK」は「種別がキャリア系」または「ブックマークあり」のとき出る。

### BOOKMARK 側
- `bookmarks.carrier` は**マスターを参照しない自由入力の文字列**（外部キーなし）。
- 種別 `carrier_type` の値は `BM_TYPES`（`FCL / LCL / AIR / RORO / BREAKBULK / general`）。**マスターの `svTypes`（`FCL CARRIER` など）とは別の値体系で、対応表は無い。**
- 見積の輸送モードとの対応は `bmTypeForTransport(transport, seaSub)`（fcl→FCL、lcl→LCL、roro→RORO、conv→BREAKBULK、air→AIR、国内手配のみ→general）。

## 4. 未決事項（着手前にユーザーと決めること）

1. **段階1から着手してよいか**（最重要）。
2. **種別の体系をどう揃えるか**：ブックマークの種別（`RORO` / `BREAKBULK` を含む）と、サブコン種別のひな形（`FCL/LCL/AIR CARRIER` のみ）が揃っていない。`RORO CARRIER` / `在来船 CARRIER`（仮称）をひな形に足すのか、ブックマークの種別を廃止して `svTypes` に一本化するのか。
3. **BOOKMARK の会社名をどう持つか**：文字列のまま（サブコンマスターの名前を候補表示するだけ）か、マスターの代表名を保存するようにするか。後者は表記ゆれが減るが、既存データの移行が要る。
4. **段階2の移行ルール**：同名が `sv` と `carrier` の両方にある場合の合流方法（詳細・別名・グループ・票）、承認制のときの扱い、移行を管理者のみに限定するか。
5. **段階3の統計への影響**：キャリア別集計（`z2Carrier` ベース）をどう置き換えるか。過去の集計結果が変わってよいか。
6. `master_votes` に `carrier` が入るか（上記「要確認」）。

## 7. 動作確認の方法

- ビルド不要。`python3 -m http.server` で開くか、`file://` でも多くは動く。
- ブラウザ自動確認は Playwright（`/opt/pw-browsers/chromium`）が使える。Supabase に実接続せず、`window.SupabaseClient` をスタブにして画面の描画・クリックを検証できる（このセッションでもこの方法で検証した）。
- 確認の例：マスターの種別が未設定でもブックマークがあれば「🔖 BOOKMARK」が出る／別名で入力しても代表名で開く／ブックマークが無ければ出ない。
