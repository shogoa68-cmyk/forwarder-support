# サイバーポート連携（第1段階・読み取りのみ）セットアップ手順

画面「📂 その他 → 🧪 CP(TEST)」の **「🔌 実接続テスト」** を動かすための準備です。設計は [サイバーポート連携_設計案.md](サイバーポート連携_設計案.md)。
認証の仕様は、公式の「【Ver.2】サイバーポート（港湾物流）API利用ガイダンス Ver.1.0」P.14・P.16〜24（引き継ぎ書 第6章）に基づきます。

## 何をするのか（全体像）

```
ブラウザ（CP(TEST)）──▶ Supabase の Edge Function「cp-proxy」──▶ サイバーポートのAPI
                          └ 接続情報・橋渡しユーザーの情報はここだけが持つ
```

- **ブラウザには秘密を置きません。** このリポジトリは公開されているので、コードに書くと誰でも見られてしまいます。
- `cp-proxy` が通すのは、**読み取り（GET）の一部だけ**です（取引の検索・操作履歴・メッセージ・COLINS の動静）。**メッセージの送信・返信・編集・削除、取引の作成・変更は、コードの上でも呼べません。**
- 利用者用のトークンは、**読み取り（read）だけの権限**で取ります（write は要求しません）。
- 使えるのは、**ログインしたチームメンバーだけ**です。

### 認証は「2つのトークン」が両方必要です

| トークン | 何を表すか | 何から取るか | APIに付けるヘッダー |
|---|---|---|---|
| ① システム用 | どのシステムか | クライアントID・クライアントシークレット | `X-Authorization`（Bearer なし） |
| ② 利用者用 | 誰として操作するか | アプリケーションID・**橋渡しユーザー**のメールアドレスとパスワード | `Authorization: Bearer …` |

> 用語：**Edge Function** ＝ Supabase の中で動く、小さなサーバー処理。**シークレット** ＝ 画面やコードには出ない「秘密の保管場所」に入れた値。**橋渡しユーザー** ＝ 「このユーザーとしてAPIを実行する」ために使う、サイバーポートの利用者アカウント。

## 手順 1：必要な情報を用意する（5つ）

### A. 会社単位の接続情報（3つ）
サイバーポートに**管理者**でログインし、**左メニュー「会社を管理する」＞ 右上「編集する」＞ 上のタブ「API接続」**で確認します。

| 名前 | 使い道 | 入れる先（Supabase の秘密） |
|---|---|---|
| クライアントID | ①システム用トークン | `CP_CLIENT_ID` |
| クライアントシークレット | ①システム用トークン | `CP_CLIENT_SECRET` |
| アプリケーションID | ②利用者用トークン | `CP_APP_ID` |

> 本番用と検証環境用で、別の組があります。**同じ環境どうし**の組を使ってください。

### B. 橋渡しユーザー（2つ）
| 名前 | 入れる先（Supabase の秘密） |
|---|---|
| 橋渡しユーザーのメールアドレス | `CP_USER_EMAIL` |
| 橋渡しユーザーのパスワード | `CP_USER_PASSWORD` |

- **このアプリ専用のユーザーを、新しく作ることをおすすめします。** サイバーポートの「更新履歴」には、このユーザーの氏名がそのまま記録されます。別のシステムのユーザーを使い回すと、どちらの操作か区別できません。
- 作り方（管理者）：**「利用者を招待する」** からAPI連携専用のユーザーを作り（グループのメールアドレスも可）、API用の**組織**に所属させて、招待メールから**初期パスワードの変更**まで済ませます。名前は「フォワーダー支援（システム連携）」のように、システムの操作だと分かるものにします。
- 組織には、運営者から会社に割り当てられた**事業種別**（海貨・通関・荷主など）が割り当たっている必要があります。

> **これらは、チャットやメール、GitHub には絶対に貼らないでください。** 次の手順で、あなたの手で Supabase にだけ入れます。

## 手順 2：Supabase にシークレットを入れて、Edge Function を置く

### 方法A：Supabase の画面だけで置く（コマンド不要）

画面の表記は少し違うことがあります。

**① シークレットを入れる**
1. Supabase にログインし、このプロジェクトの左メニュー **Edge Functions → Secrets** を開く。
2. 新しい秘密を追加する欄（Key / Value）に、次を1つずつ入れて **Save**。

   | Key | Value |
   |---|---|
   | `CP_CLIENT_ID` | クライアントID |
   | `CP_CLIENT_SECRET` | クライアントシークレット |
   | `CP_APP_ID` | アプリケーションID |
   | `CP_USER_EMAIL` | 橋渡しユーザーのメールアドレス |
   | `CP_USER_PASSWORD` | 橋渡しユーザーのパスワード |
   | `CP_ALLOWED_ORIGINS` | 画面のアドレス（`https://〇〇.github.io` の部分だけ。末尾の `/` なし） |
   | `CP_ENV`（検証環境で試すときだけ） | `sandbox`（本番のときは入れない） |

3. 値の前後の空白や引用符は、コード側で取り除きますが、できるだけ付けないでください。

**② 関数を置く**
1. 左メニュー **Edge Functions** → **Deploy a new function**（または Create a new function）→ **Via Editor** を選ぶ。（すでに `cp-proxy` を置いてあるときは、その関数を開いて、コードを入れ替える。）
2. 関数の名前を **`cp-proxy`** にする（名前は一字一句この通りに。画面の呼び出し先になります）。
3. 編集欄のコードを**すべて消す**。
4. このリポジトリの **`supabase/cp-proxy-single/index.ts`** の中身を**全部**コピーして貼り付ける（GitHub でファイルを開き、「Copy raw file」を押すとコピーできます）。
   - これは、元の `index.ts` と `logic.ts` を 1 枚にまとめた貼り付け用の版です（`node scripts/cp-tests/build-cp-proxy-single.mjs` で自動で作られます）。
5. **Deploy**（デプロイ）を押す。

**③ 「JWT の検証」をオフにする（大事）**
1. 置いた `cp-proxy` を開き、**Details**（または Settings）の **Verify JWT**（「Enforce JWT verification」などの表記）を **オフ**にして **Save changes**。
2. 理由：ブラウザが最初に送る「事前確認」の通信にはログイン情報が付かないため、オンのままだと入口で止められてしまいます。ログインとチームメンバーの確認は、`cp-proxy` が中で自分で行っています（作業フォルダの `workfolder` と同じ作りです）。

### 方法B：コマンドで置く

[Supabase CLI](https://supabase.com/docs/guides/cli) が使える PC で、このリポジトリのフォルダから実行します。

```bash
supabase login
supabase link --project-ref <プロジェクトの参照ID>
supabase secrets set CP_CLIENT_ID=<クライアントID> CP_CLIENT_SECRET=<クライアントシークレット> CP_APP_ID=<アプリケーションID>
supabase secrets set CP_USER_EMAIL=<橋渡しユーザーのメール> CP_USER_PASSWORD=<橋渡しユーザーのパスワード>
supabase secrets set CP_ALLOWED_ORIGINS=https://<公開URL>,http://localhost:18765
supabase functions deploy cp-proxy --no-verify-jwt
```

> `--no-verify-jwt` は「入口の門番を外す」意味ではありません。`cp-proxy` は中で**自分でログインの確認とチームメンバーの確認**をしています。
> パスワードに記号が含まれるときは、コマンドでは引用符で囲むか、方法Aの画面から入れるほうが確実です。

## 手順 3：画面で確かめる

1. 画面右上で **Google でログイン**します（チームメンバーのアカウント）。
2. **📂 その他 → 🧪 CP(TEST)** を開きます。
3. **① 接続情報の確認** を押します。
   - ✅ 「システム用と利用者用の両方のトークンを取得できました」と出れば成功です。「接続状態」の3行が緑になります。
   - これは**トークン（通行証）を取りに行くだけ**で、データには触れません。
4. **② 取引を検索** を押します。
   - 番号を入れると、取引番号・B/L・ブッキング・社内管理番号・インボイスのどれかが**完全一致**する取引を探します。
   - 空のままなら、**直近30日に更新された取引**を探します。
   - 「返ってきたデータそのもの」を開くと、サイバーポートが返した中身をそのまま確認できます。
5. **③ COLINS 本船の動静** を押します（取引が無くても試せます）。
   - 輸入／輸出と、**港コード**（UN/LOCODE 5桁。東京＝JPTYO、横浜＝JPYOK）を選びます。本船名で絞ることもできます。
   - ターミナル・本船名・航海番号・荷役や搬入の予定と実績・CYオープン／カットが表に出ます（日時は日本時間で表示）。
6. **④ COLINS コンテナの状況** を押します。
   - コンテナ番号、**輸入ならB/L番号、輸出ならブッキング番号**のどれかを入力します（空白は自動で除きます）。
   - 実入り／空・通関・搬出可否・CY搬入・ゲートイン／アウト・DO の状況などが表に出ます。

## うまくいかないとき

| 表示（種類） | 原因と対処 |
|---|---|
| 「サーバー側が未設定です（Edge Function「cp-proxy」を配置してください）」 | 手順 2 の関数の配置がまだです |
| 「通信できませんでした（…CP_ALLOWED_ORIGINS…）」 | `CP_ALLOWED_ORIGINS` に、いま画面を開いているアドレスが入っていません（画面のメッセージに、いまのアドレスが出ます） |
| 「サイバーポートの接続情報が未設定です」（`cp_not_configured`） | `CP_CLIENT_ID` / `CP_CLIENT_SECRET` が未登録です |
| 「API接続用ユーザーの情報が未設定です」（`cp_user_not_configured`） | `CP_APP_ID` / `CP_USER_EMAIL` / `CP_USER_PASSWORD` のどれかが未登録です |
| 「client_id / client_secret が正しくありません（invalid_client）」（`token_failed`） | クライアントID・シークレットの違いです。**同じ環境どうし**の組か、前後の空白がないか確認してください |
| 「システム用トークンの取得先がAPIではありません」（`token_wrong_endpoint`） | 取得先がウェブページに当たっています。`CP_TOKEN_URL` を設定している場合は削除してください（公式の取得先が既定です） |
| 「API接続用ユーザーのトークンを取得できませんでした」（`user_token_failed`） | アプリケーションID・メールアドレス・パスワードの違い、またはそのユーザーがAPI用に登録されていません。詳細欄の `AADB2C…` の番号を控えてください（下の表） |
| 「サイバーポートに認証を拒否されました」（`upstream_auth`） | 2つのトークンは取れたが、APIが拒否しています。ユーザーの組織・権限・事業種別を確認してください。詳細欄の文言を控えてください |
| 「該当するデータが見つかりませんでした…ETA前…」（`not_found`） | 該当する取引がない、または NACCS にまだ情報がない状態です |
| 「呼び出しが多すぎます」 | 1人あたり1分30回までの制限です。少し待ってください |

### 利用者トークンの詳細欄に出る主な番号（Azure AD B2C）

| 番号 | 意味（一般的なもの） |
|---|---|
| `AADB2C90225` | ユーザー名（メール）またはパスワードが違う |
| `AADB2C90117` | スコープが認識されない（`CP_ENV` と接続情報の環境の組み合わせ、または `CP_OPENID_SCOPE` を確認） |
| `AADB2C90205` | アプリケーションが、そのリソースへの権限を持っていない（アプリケーションIDの環境違い） |

意味が分からない番号は、そのまま控えて相談してください（パスワードなどの値は書かないでください）。

## 秘密を変えたい・止めたいとき

- **変える**：Secrets の値を入れ直す（方法B は `supabase secrets set …` をもう一度）。**再デプロイは不要**です（呼び出しのたびに読み込みます。ただし、すでに取得済みのトークンは有効期限まで使い回すため、反映まで最大で約1時間かかることがあります）。
- **止める**：Secrets から `CP_CLIENT_ID` などを削除する（画面は「未設定」と表示するだけになります）。
- **漏れたかもしれないとき**：サイバーポート側で接続情報の再発行・橋渡しユーザーのパスワード変更をしてから、上の「変える」をします。

## 守っていること

- 接続情報・パスワード・トークンは、画面にも応答にも、記録（ログ）にも出しません。
- 通すのは、許可リストにある **読み取りの GET だけ**です（`supabase/functions/cp-proxy/logic.ts` の `ALLOWED_GET`）。増やすときも、読み取りだけを足します。
- 利用者トークンは、読み取り（read）の権限だけで取ります。
- 1人あたり1分30回まで。相手先のエラーは最大3回、間隔を延ばしながら再試行します。401 のときは、トークンを両方取り直して1回だけやり直します。
- 番号は、空白を除いて大文字にそろえてから検索します（`ONEY TYOGF8748400` → `ONEYTYOGF8748400`）。

```bash
CP_TARGET=single node scripts/cp-tests/cp-proxy-test.mjs     # 貼り付け用の 1 枚版を試験
python3 -m http.server 18765 &                               # 画面の試験用にサーバーを起動
node scripts/cp-tests/cp-test-page-test.js                   # CP(TEST) の実接続欄の動き（Chromium）
```
