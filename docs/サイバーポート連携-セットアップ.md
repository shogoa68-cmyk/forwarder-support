# サイバーポート連携（第1段階・読み取りのみ）セットアップ手順

画面「📂 その他 → 🧪 CP(TEST)」の **「🔌 実接続テスト」** を動かすための準備です。設計は [サイバーポート連携_設計案.md](サイバーポート連携_設計案.md)。

## 何をするのか（全体像）

```
ブラウザ（CP(TEST)）──▶ Supabase の Edge Function「cp-proxy」──▶ サイバーポートのAPI
                          └ 接続情報（client_id / client_secret）はここだけが持つ
```

- **ブラウザには接続情報を置きません。** このリポジトリは公開されているので、コードに書くと誰でも見られてしまいます。
- `cp-proxy` が通すのは、**読み取り（GET）の一部だけ**です（取引の検索・操作履歴・メッセージ・COLINS の動静）。**メッセージの送信・返信・編集・削除、取引の作成・変更は、コードの上でも呼べません。**
- 使えるのは、**ログインしたチームメンバーだけ**です。

> 用語：**Edge Function** ＝ Supabase の中で動く、小さなサーバー処理。**シークレット** ＝ 画面やコードには出ない「秘密の保管場所」に入れた値。

## 手順 1：接続情報を用意する

サイバーポートから払い出された次の2つです。

| 名前 | 中身 |
|---|---|
| `client_id` | システム用の ID |
| `client_secret` | システム用のパスワード |

> **この2つは、チャットやメール、GitHub には絶対に貼らないでください。** 次の手順で、あなたの手で Supabase にだけ入れます。
> 更新履歴に残る名前は、この接続情報に結びついた利用者の名前になります。**個人ではなく連携専用のアカウント**に結びついたものを使ってください（→ 設計案「未決事項」）。

## 手順 2：Supabase にシークレットを入れて、Edge Function を置く

[Supabase CLI](https://supabase.com/docs/guides/cli) が使える PC で、このリポジトリのフォルダから実行します（作業フォルダの手順 4 と同じ準備です。すでに `supabase login` と `supabase link` が済んでいれば、その部分は不要です）。

```bash
supabase login
supabase link --project-ref <プロジェクトの参照ID>
```

接続情報を入れます（`<…>` は自分の値に置き換えます）。

```bash
supabase secrets set CP_CLIENT_ID=<client_id> CP_CLIENT_SECRET=<client_secret>
```

画面を公開している URL を「許可するアクセス元」として登録します（カンマ区切り。例は GitHub Pages とローカル確認用）。

```bash
supabase secrets set CP_ALLOWED_ORIGINS=https://<公開URL>,http://localhost:18765
```

Edge Function を置きます。

```bash
supabase functions deploy cp-proxy --no-verify-jwt
```

> `--no-verify-jwt` は「入口の門番を外す」意味ではありません。`cp-proxy` は中で**自分でログインの確認とチームメンバーの確認**をしています（作業フォルダの `workfolder` と同じ作りです）。

### 手順 2 の別の方法：Supabase の画面だけで置く（コマンド不要）

コマンドを使わずに、ブラウザの画面だけで済ませる方法です（画面の表記は少し違うことがあります）。

**① シークレットを入れる**
1. Supabase にログインし、このプロジェクトの左メニュー **Edge Functions → Secrets** を開く。
2. 新しい秘密を追加する欄（Key / Value）に、次の3つを1つずつ入れて **Save**。
   - `CP_CLIENT_ID` ＝ クライアントID
   - `CP_CLIENT_SECRET` ＝ クライアントシークレット（**ID と同じ組**のもの）
   - `CP_ALLOWED_ORIGINS` ＝ 画面のアドレス（`https://〇〇.github.io` の部分だけ。末尾の `/` なし）
3. 値の前後に空白や引用符（" '）を付けない。

**② 関数を置く**
1. 左メニュー **Edge Functions** → **Deploy a new function**（または Create a new function）→ **Via Editor** を選ぶ。
2. 関数の名前を **`cp-proxy`** にする（名前は一字一句この通りに。画面の呼び出し先になります）。
3. 編集欄に最初から入っているサンプルのコードを**すべて消す**。
4. このリポジトリの **`supabase/cp-proxy-single/index.ts`** の中身を**全部**コピーして貼り付ける（GitHub でファイルを開き、「Copy raw file」を押すとコピーできます）。
   - これは、元の `index.ts` と `logic.ts` を 1 枚にまとめた貼り付け用の版です（`node scripts/cp-tests/build-cp-proxy-single.mjs` で自動で作られます）。
5. **Deploy**（デプロイ）を押す。

**③ 「JWT の検証」をオフにする（大事）**
1. 置いた `cp-proxy` を開き、**Details**（または Settings）の **Verify JWT**（「Enforce JWT verification」などの表記）を **オフ**にして **Save changes**。
2. 理由：ブラウザが最初に送る「事前確認」の通信にはログイン情報が付かないため、オンのままだと入口で止められてしまいます。ログインとチームメンバーの確認は、`cp-proxy` が中で自分で行っています（作業フォルダの `workfolder` と同じ作りです）。

## 手順 3：画面で確かめる

1. 画面右上で **Google でログイン**します（チームメンバーのアカウント）。
2. **📂 その他 → 🧪 CP(TEST)** を開きます。
3. **① 接続情報の確認** を押します。
   - ✅ 「トークンを取得できました」と出れば成功です。「接続状態」の3行が緑になります。
   - これは**トークン（通行証）を取りに行くだけ**で、データには触れません。
4. **② 取引を検索** を押します。
   - 番号を入れると、取引番号・B/L・ブッキング・社内管理番号・インボイスのどれかが**完全一致**する取引を探します。
   - 空のままなら、**直近30日に更新された取引**を探します。
   - 「返ってきたデータそのもの」を開くと、サイバーポートが返した中身をそのまま確認できます。

## うまくいかないとき

| 表示 | 原因と対処 |
|---|---|
| 「サーバー側が未設定です（Edge Function「cp-proxy」を配置してください）」 | 手順 2 の `supabase functions deploy cp-proxy --no-verify-jwt` がまだです |
| 「通信できませんでした（…CP_ALLOWED_ORIGINS…）」 | 手順 2 の `CP_ALLOWED_ORIGINS` に、いま画面を開いている URL が入っていません（`https://` から始まる、末尾の `/` なしの形） |
| 「サイバーポートの接続情報が未設定です」（`cp_not_configured`） | `CP_CLIENT_ID` / `CP_CLIENT_SECRET` が未登録です。`supabase secrets set` をやり直してください |
| 「トークンを取得できませんでした（401 など）」（`token_failed`） | `client_id` / `client_secret` の入力ミス、または失効です。入れ直してください。詳細欄に相手先の説明が出ます |
| 「トークンの取得先に接続できませんでした」（`token_network`） | トークンの取得先に届きません。下の「トークンの取得先」を見てください |
| 「サイバーポートに認証を拒否されました」（`upstream_auth`） | トークンは取れたが、APIが拒否しました。下の「認証が二重の可能性」を見てください |
| 「該当するデータが見つかりませんでした…ETA前…」（`not_found`） | 該当する取引がない、または NACCS にまだ情報がない状態です |
| 「呼び出しが多すぎます」 | 1人あたり1分30回までの制限です。少し待ってください |

### トークンの取得先

Swagger の画面は、同じサイト（`swagger.cyber-port.net`）の `POST /vendor-auth/token` に `client_id` と `client_secret` を送ってトークンを取っています。**実際に確かめた結果（2026-11-10）**：

- `https://swagger.cyber-port.net/vendor-auth/token` ……トークンの取得口です。偽の値を送ると `invalid_client`（ID が正しくない）という JSON が返ります。`cp-proxy` の**初期値**はここです。
- `https://api.cyber-port.net/vendor-auth/token` ……ウェブサイトの案内ページ（HTML）が返るだけで、トークンの取得口ではありません。

取得先を変えたいとき（払い出し元から別の取得先を案内されたときなど）だけ、`CP_TOKEN_URL` を設定します（`supabase secrets set CP_TOKEN_URL=…`、または画面の Secrets）。

| 表示 | 意味 |
|---|---|
| 「トークンの取得先がAPIではありません（ウェブページが返りました）」（`token_wrong_endpoint`） | 取得先がウェブページに当たっています。`CP_TOKEN_URL` を確認してください |
| 「client_id / client_secret が正しくありません（invalid_client）」 | 取得先は正しく、ID かシークレットが違います。**同じ組**（本番どうし・検証環境どうし）か確認してください |

### 認証が二重の可能性

公式のAPI仕様では、すべてのAPIの認証が「`X-Authorization`（システム用のトークン）**と** `openid`（利用者としてのログイン）」の両方になっています。

- ① は成功するのに、② で「認証を拒否されました」（`upstream_auth`）になる場合は、**利用者ログインのトークンも必要**かもしれません。
- その場合は、**詳細欄に出る「サイバーポートの応答コード」と「詳細」の文言**を、控えてから相談してください（接続情報の値は書かないでください）。

## 接続情報を変えたい・止めたいとき

- **変える**：`supabase secrets set CP_CLIENT_ID=… CP_CLIENT_SECRET=…` をもう一度実行します。再デプロイは不要です（呼び出しのたびに読み込みます）。
- **止める**：`supabase secrets unset CP_CLIENT_ID CP_CLIENT_SECRET` で消します（画面は「未設定」と表示するだけになります）。
- **漏れたかもしれないとき**：サイバーポート側で接続情報を再発行してもらい、上の「変える」をします。

## 守っていること

- 接続情報・トークンは、画面にも応答にも、記録（ログ）にも出しません。
- 通すのは、許可リストにある **読み取りの GET だけ**です（`supabase/functions/cp-proxy/logic.ts` の `ALLOWED_GET`）。増やすときも、読み取りだけを足します。
- 1人あたり1分30回まで。相手先のエラーは最大3回、間隔を延ばしながら再試行します。
- 番号は、空白を除いて大文字にそろえてから検索します（`ONEY TYOGF8748400` → `ONEYTYOGF8748400`）。

## 試験（開発者向け）

サイバーポートには接続しません（通信は偽物に差し替えます）。

```bash
node scripts/cp-tests/cp-proxy-test.mjs                 # Edge Function の判断・認証・再試行・秘密が漏れないこと（Node 22.13 以上）
python3 -m http.server 18765 &                          # 画面の試験用にサーバーを起動
node scripts/cp-tests/cp-test-page-test.js              # CP(TEST) の実接続欄の動き（Chromium）
```
