# サイバーポート「毎朝・毎夕の動静確認」自動化ロードマップ

作成: 2026-11-10 / 状態: 計画（コード変更なし）
前提: 当面は **読み取りのみ**（書き込みはしない）。設計の土台は [サイバーポート連携_設計案.md](サイバーポート連携_設計案.md)、手順は [サイバーポート連携-セットアップ.md](サイバーポート連携-セットアップ.md)。

## 1. ゴール

担当者が毎朝・毎夕に「動静を見に行く」作業をなくし、**アプリが代わりに確認して、変わったことと要対応だけを知らせる**。

| 時刻（案） | 役割 | 出すもの |
|---|---|---|
| 毎朝 8:30 | 「今日やること」の確認 | 今日・明日動く案件／ETA・ETDの変更／搬出可になったコンテナ／フリータイム期限が近い（48時間以内）・超過 |
| 毎夕 16:30 | 「日中の変化」の確認 | 朝から変わった点（ETA変更・実績確定・搬入完了）／明日の予定／未解決の要対応 |

※時刻は変更できる設定にする（サーバー上の予約は UTC で持つ。8:30 JST ＝ 前日 23:30 UTC）。

## 2. 分かっていること（調査済み）

- **サイバーポート自身が COLINS の情報で帳票を自動更新する**（照合キーがそろうとき）。こちらから上書きする必要はなく、**帳票・COLINS を読み取るだけで最新が分かる**。
  - 本船の動静（ETA/ETD・ATA/ATD・CYオープン/カット）：キー＝船社コード＋本船名（またはコールサイン）＋航海番号
  - 輸出コンテナ（搬出入の日時・場所）：キー＝ブッキング番号＋コンテナ番号
  - 輸入の搬出可否・**搬出期限日（フリータイム）**：キー＝B/L番号＋コンテナ番号
  - 対象は東京・川崎・横浜・名古屋・大阪・神戸など**対象ターミナルのみ**。対象外の港・LCL（CFS倉庫）は NACCS の貨物情報照会（ICG）で補う。
- 必要な読み取り API はすべて GET。`cp-proxy` の許可リストには、すでに取引（`Trades/Search`・`Get`・`GetContainers`）・操作履歴・チャットの読み取り・COLINS（`ColinsViewers/*`）・ターミナルが入っている。**帳票の読み取り（`Trades/Reports/GetList`・`Get`）と EDIFACT の読み取り（`ParseEdifacts/ParsedContents/Search`・`GetContent`）は未登録なので、許可リストへの追加が必要**。
- Webhook（サイバーポートからの通知）でも変化に気づける。署名（HMAC-SHA256）の確認が必要。送信元 IP は固定されない。

## 3. 最大の壁と解決方針

**壁：今の `cp-proxy` は「ログイン中の人」の呼び出ししか受け付けない。** 朝夕の自動実行には人がいない。

**解決：自動実行専用の入口 Edge Function `cp-watch` を新設する。**
- 呼び出せるのは、Supabase の定期実行（`pg_cron`＋`pg_net`）だけ。専用の秘密の合言葉（ヘッダー）で確認する。
- 呼べる API は、動静確認に必要な読み取りの GET だけに限定する。
- トークン取得・再試行・呼び出し回数の制限は、`cp-proxy` の共通部品（`logic.ts`）を使い回す。
- `pg_cron` は既にこのリポジトリで使っている（`docs/sql/feedback-reports.sql`）。

## 4. 段階（フェーズ）

各フェーズの完了条件を満たしてから次へ進む。大きさ：S＝小・M＝中・L＝大。

### フェーズ 0：準備（人の作業・コードなし）　S
- [ ] 橋渡しユーザーを、取引を行う**すべての自社組織**に所属させる（未所属の組織の取引・EDIFACT は見えない）。
- [ ] 橋渡しユーザーに管理者権限を付ける（Webhook 履歴取得などの管理系に必要）。
- [ ] まず**検証環境**で試すか、本番か、を決める。
- [ ] 通知の出し方を決める（下の「決めること」）。
- **完了条件**：実機で、橋渡しユーザーが対象の取引を検索で取得できる（いま確認中の `Trades/Search` が通る）。

### フェーズ 1：案件と取引のひもづけ　M
- 見積案件ごとに「動静を追う」スイッチと、照合キー（B/L番号・ブッキング番号・コンテナ番号・本船名・航海番号）を持つ。
- 取引番号との対応表 `cp_deal_links`（設計案どおり）を作る。
- 案件画面に「今すぐ確認」ボタン（人が押すと、いまの動静を1件だけ表示）。ここで**見せ方と判定の言葉を固める**。
- **完了条件**：1つの実案件で、キーを入れて押すと ETA・搬出可否が表示される。

### フェーズ 2：変化を見つける仕組み（差分）　M
- 取得した結果を**スナップショット**（その時点の写し）として保存し、前回と比べて**変わった項目だけ**を `cp_changes` に残す。
- 追う項目：ETA/ETD・ATA/ATD・CYオープン/カット・搬出可否・搬出期限日・ゲートイン/アウト・DO入手・検査状況。
- 人が手で入力した値は**上書きしない**。自動取得は別枠「サイバーポート最新状況（取得日時つき）」に持つ。
- 判定ルール：期限まで48時間以内＝警告、超過＝赤、ETA が1日以上ずれた＝要確認。
- **完了条件**：サンプルの前回／今回の2件の写しから、正しい変化一覧ができる（偽の応答での自動テスト）。

### フェーズ 3：朝夕の自動実行　L
- 新設 `cp-watch`（Edge Function）を、`pg_cron` が朝夕に呼ぶ。
- 追跡中の案件を**小分けに**処理する（Edge Function の実行時間に上限があるため）。呼び出し回数の上限（1分30回）の範囲に収める。
- 失敗の扱い：相手先エラーは指数バックオフ（待ち時間を倍々に延ばして再試行）で最大3回。「ETA前でNACCS未登録」と「通信エラー」は区別して表示。
- 実行記録 `cp_watch_runs`（いつ・何件・成功/失敗）を残し、**動かなかった朝・夕に気づける**ようにする。
- **完了条件**：検証環境で、予約の時刻に自動で動き、変化が `cp_changes` に入る。止まったときに画面で分かる。

### フェーズ 4：知らせる（朝夕のダイジェスト）　M
- ダッシュボードの先頭に「🚢 今朝の動静／今夕の動静」カード（要対応→変更→予定の順）。
- 件数のバッジ（赤：期限超過／橙：48時間以内／青：変更あり）。案件カードにも印。
- 見たら既読にする（既読は人ごと）。
- 任意：メールなど外への通知（決めること参照）。
- **完了条件**：朝に開くと、要対応が上に並んでいる。既読が効く。

### フェーズ 5：Webhook と EDIFACT（すぐ気づく・突き合わせる）　L
- `cp-webhook`（Edge Function）を新設し、通知の署名を確認してから `cp_events` に記録する。
- 通知を受けたら、その取引だけを即時に再確認する（朝夕の定期確認は残す＝取りこぼしの保険）。
- EDIFACT（ONE・MSC など）を読み取り、**アプリの案件との差**を表示する（反映は人が確認して行う）。
- 取引へ「適用」する操作（`ParsedContents/Apply`）は**使わない**（書き込みのため）。
- **完了条件**：検証環境で、通知から1分以内に変化が画面に出る。

### フェーズ 6：仕上げ（任意）　M
- 対象外の港・LCL は NACCS の貨物情報照会（ICG）へ自動で切り替える。
- ATD/ATA の確定を、売上計上日の「候補」として案件に提案する（自動では書き換えない）。
- 週次のまとめ、担当者別の絞り込み。

## 5. 全体の見通し

```
準備(0) → ひもづけ(1) → 差分(2) → 朝夕の自動実行(3) → 知らせる(4) → Webhook/EDIFACT(5) → 仕上げ(6)
 人の作業     画面            中身         ここで「自動化」達成   ここで「使える」    すぐ気づく
```
**フェーズ 3＋4 が終わった時点で、「毎朝・毎夕の動静確認を自動化したい」は達成**。フェーズ 5 以降は精度と速さの改善。

## 6. 守ること（安全）
- 書き込みはしない。許可するのは読み取りの GET だけ（許可リストで強制）。
- 接続情報・パスワードは Supabase の secrets のみ。リポジトリ・ブラウザ・ログ・応答には出さない。
- `cp-watch` は予約からの呼び出しだけを受け付ける（秘密のヘッダー）。ログインなしで誰でも叩けないようにする。
- 顧客情報を含む取得結果は、ログイン済みのチームメンバーだけが見られる（RLS）。**公開リポジトリには書き出さない**。
- すべての自動テストは、サイバーポートへつながない偽の応答で行う（既存の `scripts/cp-tests/` と同じ方式）。

## 7. 決めること（ユーザー確認）

1. **対象の案件**：受注済みだけ？「提示済み」も？ 完了（ATA確定後 N 日）で自動的に追跡を終えるか。
2. **朝夕の時刻**：8:30／16:30 でよいか。土日・祝日は止めるか。
3. **通知の出し方**：アプリ内（ダッシュボード）だけで足りるか。メール・チャットなど外への通知も必要か（要る場合は送信先のサービスと、ネットワーク許可の追加が要る）。
4. **本番か検証環境か**：最初は検証環境で通しで動かすか。
5. **追う案件の数の目安**：1回の確認で何件ぐらいか（回数制限と実行時間の設計に影響）。
6. **輸入と輸出**：どちらを先にするか（輸入＝搬出期限の監視、輸出＝コンテナ番号・CY搬入の回収）。

## 8. 用語
- **Edge Function**：Supabase の上で動く小さなサーバー側プログラム。
- **pg_cron**：データベースの「予約実行」。決めた時刻に処理を呼び出す。
- **スナップショット**：その時点の状態の写し。前回と比べて「何が変わったか」を調べるために保存する。
- **Webhook**：サイバーポートが「変化があったよ」と、こちらへ知らせてくる通知の仕組み。
- **HMAC-SHA256 署名**：通知が本物かを確かめる、秘密の合言葉を使った確認の方法。
- **COLINS**：港のコンテナターミナルの搬出入などの情報を集めたサービス。サイバーポートと連携している。
