# マスターの変更履歴：設計案（最初の一歩）

> 2026-11-11。設計思想（[設計思想-共同で育てる知識.md](設計思想-共同で育てる知識.md)）の「③改ざん耐性」「④透明性」の土台。
> **SQL は案であり、Supabase ではまだ実行していない。** 実行するまで、アプリには何も影響しない。

## 1. 何を作るか

マスター関連の表への「追加・変更・削除」を、**変更前と変更後の中身つき**で自動的に記録する履歴の表 `master_history`。

- 記録は DB のトリガーが行う → **アプリ（JS）は 1 行も変えない**。
- 履歴は**追記のみ**。アプリからも、DB の持ち主・`service_role` からも、書き換え・削除・TRUNCATE はできない（トリガーで拒否）。
- 実行した時点の既存データを「出発点（BASELINE）」として 1 回だけ記録する。以降の変更の比較元になる。
- SQL：[sql/master-history.sql](sql/master-history.sql)　テスト：`scripts/sql-tests/master-history-sql-test.sh`（26 項目・使い捨ての PostgreSQL で確認済み）

## 2. 記録する表

| 表 | 何が入っているか | 記録される操作の例 |
|---|---|---|
| `master_votes` | マスターの登録（1 人 1 行） | 登録・解除 |
| `synonym_groups` | 代表名と別名 | 別名の追加・外す・代表名の変更・まとめる |
| `master_details` | 詳細（ふりがな・担当者・国・取引形態など） | 詳細の編集 |
| `master_attachments` | 添付ファイルの情報（中身ではなく名前・場所） | 添付の追加・削除 |
| `master_requests` | 承認制の申請 | 申請・承認・却下 |
| `alias_rules` | エイリアス是正の規則 | 規則の追加・変更・削除（表がある環境のみ） |

表が無い環境（その機能の SQL をまだ実行していない）では、その表のトリガーを作らずに飛ばす。

## 3. 履歴の中身

`master_history`：いつ（`changed_at`）／誰が（`changed_by`＝ログイン中のメール。DB から直接なら `system:<ロール名>`）／どの表の（`source_table`）／何をした（`action`＝INSERT・UPDATE・DELETE・BASELINE）／どの名前の（`field`・`value`）／変更前（`old_data`）／変更後（`new_data`）。

- 更新日時だけが変わった「実質変更なし」の更新は記録しない（ノイズ防止）。
- **削除しても中身が `old_data` に残る**ので、「いつ・誰が消したか」と元の中身が分かる。設計思想の「削除は無効化で履歴に残す」に近い効果が、既存の表を変えずに得られる。
- 読めるのはチームメンバー全員（`is_team_member()`）。メンバー以外には 0 件に見える。

## 4. 既存データ・既存機能との互換性の確認

| 観点 | 結果 |
|---|---|
| 既存の表・列・ポリシー | 変更しない（トリガーを足すだけ） |
| アプリのコード | 変更不要。保存・投票・承認制・別名・詳細編集の動きは同じ |
| 既存データ | 変更しない。出発点として複製（読み取り）して記録するだけ |
| 何度実行しても安全か | 安全（テストで 2 回流して二重記録がないことを確認） |
| 承認制の流れ | 申請（INSERT）と承認（UPDATE）の両方が記録される |
| 元に戻したいとき | 各表の `trg_master_history` トリガーを `drop trigger` すれば記録が止まる。履歴の表そのものは、設計上、消せない（消すには持ち主がトリガーを先に外す） |
| 性能・容量 | 1 回の操作で 1 行増える。港プリセット登録（約 430 港）のような一括登録は数百行。10〜30 人の利用なら無料枠で十分 |

## 5. まだ記録しないもの（正直な限界）

- **案件（`quote_presets`）の変更**：今は上書き。案件データは大きいので、履歴の持ち方を別に設計する（次段階以降）。
- **「過去データの一括置換」**（エイリアス是正）：案件データを書き換える操作。規則（`alias_rules`）は記録されるが、置換で変わった案件側の中身は記録されない。
- **Supabase の持ち主による無効化**：持ち主がトリガーを外せば履歴を止められる。検知する仕組み（各行に前の行の指紋＝ハッシュを持たせる鎖）は入れていない。必要になったら追加する。
- **保存領域のファイルの中身**：添付は名前・場所だけ記録する。

## 6. 実行の手順（管理者が行う）

1. Supabase ダッシュボード → SQL Editor に [sql/master-history.sql](sql/master-history.sql) を貼って Run。
2. 動作確認：SQL の末尾の「動作確認」の `select` を流し、出発点（BASELINE）が入っていることを見る。
3. アプリでマスターを 1 件登録して消し、履歴に 2 行（INSERT と DELETE）増えることを見る。
