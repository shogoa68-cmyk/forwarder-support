# マルチテナント化 棚卸し（読み取り調査・2026-11-17）

> **目的**：SaaS 化（複数の会社が 1 つのアプリを使う）の最大の山場「会社ごとのデータ分離」に何が必要かを洗い出す。**コードもデータベースも変更していない**（調べただけ）。
> 方針は [PRODUCT_VISION.md](../PRODUCT_VISION.md) の「💰 収益化方針」を参照。

> 💡 **用語**
> - **テナント**＝契約している 1 社のこと（マンションの「1 部屋」）。
> - **RLS（Row Level Security）**＝「この行はこの人にだけ見せる」をデータベース側で強制する仕組み。
> - **`tenant_id`**＝各行に付ける「どの会社のデータか」の印。

---

## 1. いまの作り（調査でわかったこと）

| 項目 | 現状 |
|---|---|
| 構成 | Supabase 1 プロジェクト＝**1 チーム専用**。`cloud-config.js` に URL とキーが 1 組だけ |
| テーブル | SQL ファイルで確認できたもの 約 45 個＋画面が使うもの（下記の「定義が無い」4 つ） |
| 見える範囲の判定 | 関数 `is_team_member()` が **182 行**で使われている（許可リスト `allowed_emails` に載っていれば全部見える） |
| 管理者の判定 | `get_my_role()`（26 行）。`allowed_emails.role` を返す |
| ファイル置き場 | Storage のバケット 6 個（`quote-attachments`・`master-attachments`・`bookmark-files`・`local-charge-files`・`feedback-attachments`・`work-folders`） |
| サーバー処理 | Edge Function 3 本（`cp-proxy`・`cp-webhook`・`workfolder`） |
| 「組織・チーム」 | `organizations`／`teams` は**名簿の整理だけ**。見える範囲は変えていない（テナントとは別物） |

### ⚠️ 見つかった問題：核になる定義がリポジトリに無い

次の 5 つは**画面が使っているのに、`CREATE TABLE`／`CREATE FUNCTION` がリポジトリのどこにも無い**（Supabase の画面で直接作ったと思われる）。

- テーブル：`quote_presets`（案件の本体）・`allowed_emails`（許可リスト）・`row_patterns`
- 関数：`is_team_member()`・`get_my_role()`・`get_my_member_no()`

**分離の工事では、まさにここが中心になる。** 最初に、いまの Supabase から定義を書き出してリポジトリに保存する必要がある（`scripts/sql-tests/` の試験は簡易版の複製を使っている）。

## 2. テーブルの分類

### A. 会社のデータ → `tenant_id` が必要（ほぼ全部）

| グループ | テーブル |
|---|---|
| 案件 | `quote_presets`・`quote_comments`・`quote_attachments`・`quote_preset_links`・`row_patterns`・`email_import_unread` |
| マスター | `master_votes`・`master_details`・`master_attachments`・`master_requests`・`master_news`・`synonym_groups`・`alias_rules`・`drift_log`・`stats_exclusions`・`translation_dict` |
| 取引ルール・カルテ | `customer_rules`・`customer_cases` |
| 定型文 | `remark_presets`・`remark_preset_verifications` |
| ブックマーク | `bookmarks`・`bookmark_history`・`bookmark_clicks`・`bookmark_verifications`・`carrier_contacts`・`carrier_relations` |
| 料金・カレンダー | `local_charges`・`charge_notices`・`calendar_holidays`／`_history`・`calendar_surcharges`／`_history` |
| 連携 | `cp_events`・`cp_changes`・`cp_watch_targets`・`cp_watch_runs` |
| 名簿 | `allowed_emails`・`user_profiles`・`organizations`・`teams`・`org_members`・`team_members` |
| お知らせ | `announcements`（テナント管理者が自社向けに出す） |

### B. すでに「本人だけ」の作り（分離はほぼ済み）

`wf_nodes`・`wf_config`（作業フォルダ。本人の行だけ）。ただし**容量の上限**はテナント／プランに合わせて見直しが必要。

### C. 運営者（あなた）向け → 扱いを決める必要あり

`feedbacks`・`feedback_comments`・`feedback_votes`・`feedback_export_keys`。
いまは「メンバー全員が全員の不具合報告を読める」。SaaS では **他社の報告（顧客名の写ったスクショ含む）が見えてはいけない**。報告は「運営者だけが全社分を読める／各社は自社分だけ」に変える。

### D. 全社共通のままでよいもの

`data/carriers.js`・`incoterms.js` などの内蔵データ（コード側）。ブックマークの初期投入（シード）は「新しい会社を作るときの雛形」として扱う。

## 3. 分離の方針案（たたき台）

**「1 つのデータベースに全社を入れ、`tenant_id` と RLS で分ける」**を推奨（会社ごとに別プロジェクトにするより運営が楽・安い）。

1. 新テーブル `tenants`（会社）を作る。`organizations`（組織）は `tenant_id` を持たせ、**テナント＞組織＞チーム**の 3 段にする。
2. `allowed_emails` に `tenant_id` を足し、**1 メール＝1 テナント**から始める（兼務は後回し）。
3. 関数 `my_tenant_id()` を作る（ログイン中の人の会社を返す）。
4. **各テーブルの `tenant_id` に `default my_tenant_id()` を付ける**＋挿入時に必ず自分の会社で上書きするトリガー → 画面側の保存処理はほとんど変えずに済み、他社の印を偽って書くこともできない。
5. 既存のポリシーは `is_team_member()` を使っているので、**この関数を「同じ会社のメンバーか」に書き換える**＋各ポリシーに `tenant_id = my_tenant_id()` を足す（182 行を一括で全面書き直すのではなく、入口で絞る）。
6. Storage は、保存パスの先頭を `{tenant_id}/…` にして、ポリシーで同じ会社だけに許す（既存ファイルの移行が必要）。
7. SECURITY DEFINER の関数（編集ロック `quote_*_lock`・作業フォルダ `wf_*`・`cp_watch_*` など約 35 本）は **RLS を素通りする**ので、1 本ずつ「他社の行を触れない」ことを確認する。

### 先に決めたいこと

| # | 論点 | 選択肢 | 私の推奨 |
|---|---|---|---|
| 1 | **本番のデータベース** | ① いまの Supabase プロジェクトに作り込む（既存チーム＝テナント 1 号）／② **SaaS 用に新しいプロジェクトを作る** | ②（既存チームのデータに影響しない・勤務先のデータが混ざらない。要相談） |
| 2 | 1 人が複数の会社に属せるか | 1 メール＝1 テナント／複数可 | 最初は 1 メール＝1 テナント |
| 3 | 不具合報告・アイデア投票 | 全社共通の掲示板／会社ごと | 不具合は会社ごと＋運営者が全部読める。アイデア投票は共通にするか別途相談 |

## 4. Edge Function・外部連携（個別の作り直しが必要）

| 機能 | 現状 | SaaS での課題 |
|---|---|---|
| `workfolder`（ドライブ版） | **管理者 1 人の Google ドライブ**に保存 | 他社のファイルをあなたのドライブに置くことになる → **SaaS では Supabase 保存領域版だけ**にする（ドライブ版は使わない） |
| `cp-proxy`（サイバーポート） | 1 組の接続情報を前提（Secrets は `CP_ALLOWED_ORIGINS` など） | 会社ごとにサイバーポートの契約・接続情報が違う → **会社ごとの接続情報を暗号化して保存**する仕組みが必要。そもそも他社向けに提供してよいか、**サイバーポート側の利用条件の確認が必要（未確認）** |
| `cp-webhook` | 秘密 `CP_WEBHOOK_SECRET` が 1 つ | 会社ごとに受け口（URL か秘密）を分ける |
| `cp-proxy` の予約実行（`watch_run`） | 全案件を順に確認 | 会社をまたいで回す・会社ごとの上限（呼び出し回数）を持つ |
| Google ログイン | 招待（許可リスト）方式 | **自分で登録→会社を作る**入口が要る（段階 2） |

## 5. 作業の分け方（段階 1 を小さく切る）

> 随時の作業でも 1 つずつ完成させられる単位にしてある。**上から順に。各ステップに「他社が見えない」自動試験を足す。**

| # | 作業 | 内容 | 規模 |
|---|---|---|---|
| 1-0 | **定義の書き出し** | いまの Supabase から `quote_presets`・`allowed_emails`・`row_patterns`・上記 3 関数の定義を取り出し、`docs/sql/` に保存 | 小 |
| 1-1 | 論点の決定 | 上の表の 3 つ | 小 |
| 1-2 | 土台 | `tenants`・`my_tenant_id()`・`allowed_emails.tenant_id`・既存データを「テナント 1 号」に | 中 |
| 1-3 | `tenant_id` の追加 | グループ A を 4〜5 回に分けて追加（案件 → マスター → ブックマーク …） | 大（分割） |
| 1-4 | ポリシーの置き換え | `is_team_member()` の書き換え＋各ポリシー | 大 |
| 1-5 | Storage | バケット 6 個のパス・ポリシー | 中 |
| 1-6 | SECURITY DEFINER 関数の点検 | 約 35 本を 1 本ずつ | 中 |
| 1-7 | **分離の試験** | 使い捨ての PostgreSQL で「会社 A のユーザーが会社 B の行・ファイルを読む／書く／消す／関数経由で触る」がすべて拒否されることを確認（`scripts/sql-tests/tenant-isolation-sql-test.sh`） | 大 |
| 1-8 | 画面側 | 保存処理の確認・管理画面の見直し（登録の入口は段階 2） | 中 |

**これが済むまで、外部の会社には出さない。**
